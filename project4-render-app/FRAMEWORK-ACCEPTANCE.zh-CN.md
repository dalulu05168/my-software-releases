# P004 三层交易平台：功能框架、权限及验收清单

更新：2026-10-11。开发分支：`p004-account-flow-readonly-20261011`（源于 `p004-light-ui-render-20261011`）。本分支不部署、不合并 main，不触碰生产账户或资金。

## 1. 唯一账户结构

- `master` 总账户：后台登录（账号/密码/TOTP），能列出全部运营子账户，选择某个子账户查看它的客户；可不加筛选查询全部客户。
- `ops` 子账户：后台登录（账号/密码/TOTP），直接进入属于自己的客户列表；服务端必须强制限定身份绑定的 `ops_account_id`。
- `client` 客户：独立客户端登录，持仓与订单仅限本人身份，只读。不得通过后台页面或模拟镜像取得其他客户数据。

## 2. 本轮实现（只读查询，不进行交易）

1. 总账户 `子账户 → 查看所属客户 → 客户详情 → 订单 / 持仓 / 资金申请`；
2. 子账户 `会员管理 → 所属客户 → 客户详情 → 订单 / 持仓 / 资金申请`；
3. 客户列表和每客户详情使用后台只读 API，而非硬编码的 `initialCustomers` / `stocks`；
4. 报表后端新增两个可选过滤参数：`ops_account_id`、`user_id`。总账户可按子账户筛选；子账户无论传什么查询参数，都由服务器强制使用自己绑定的 ID，若传了不属于自己的 `ops_account_id`，返回 403；订单、资金、持仓分别按客户 ID 严格筛选；
5. 若数据库查询失败，则返回错误，不提供虚构的订单/余额；
6. 客户列表 CSV 仅导出当前已加载行（最多 200 条），不假称全量下载。

## 3. 数据流向

```text
master / ops 登录
  -> 服务器验证对应后台 session + role
  -> master 获取运营账户列表或 ops 进入所属客户
  -> GET project4-reporting-api?action=clients[&ops_account_id=...]
  -> 点击客户，取实际 user_id
  -> GET project4-reporting-api?action=orders|positions|cash&user_id=...[&ops_account_id=...]
  -> 服务器进行 user_id + ops_account_id 的联合权限过滤
  -> 页面只显示数据库返回的行
```

此外，client 使用 `project4-client-api` 的 login / portfolio / logout 等接口，与后台令牌互不通用。

## 4. 重要边界（不能称为已完成）

- **客户自助注册**：已核对线上客户端 Edge Function 存在 `?action=register` 和数据库 `register_client_with_invite` 事务，注册会绑定邀请码所属 OPS、默认 KYC=PENDING、交易/提现禁用。本分支已同步该接口并将邀请码校验改为六位数字，但尚未部署到生产、也未执行端到端验收；不能声称新六位规则已在线可用。
- **APP 镜像**：旧 `AppMirror` 组件含预设股票与客户数据，当前没有挂接在最新版真实客户列表上。不可当作真实客户手机；后续仅能对接同一权限范围内的实际客户 API 生成只读业务视图。
- **余额/入金/提现/下单**：真实资金账本、交易执行及审批接口未完成；保持关闭。
- **产品、风控、审计、通知、客服**：多数为未接入占位入口；不能将旧组件演示交互当做可用功能。
- **证券外部查询**：原证券管理 UI 还存在本地伪候选结果逻辑；必须改为真实 provider 查询并核对代码、市场、交易所后才能上线。
- **持久化与生产验证**：本次仅 GitHub 前端构建与静态回归通过，未核查生产 Supabase 部署、数据库迁移、真实数据以及浏览器中的登录与操作。CI 不是端到端数据库验收。

## 7. 创建子账户必须同时产生的两套凭证（用户原始要求，2026-10-11纠正）

**同一个创建动作的服务器职责**：MASTER 提交 OPS 名称、账号、密码和市场权限；服务器生成独立 TOTP 密钥（用于 OPS 登录时的动态六位验证码），同时生成一个固定的、唯一的 **6 位纯数字**邀请码（用于此 OPS 的客户注册）。创建成功后返回 OPS ID、邀请码、一次性 2FA 绑定密钥与 otpauth URI。

- 六位纯数字邀请码：正则 `^[0-9]{6}$`，允许首位是 0；不使用 `OPS-`、字母或可变长度。使用加密安全随机数，数据库 `ops_invite_codes.code_digest` 唯一索引碰撞时必须重新生成，且通过外键绑定 `ops_account_id`。
- 邀请码是固定客户注册链接凭证：属于哪个 OPS 就把注册成功的 `identities.ops_account_id`、`client_accounts.ops_account_id` 和 `client_registration_attribution` 一起指向该 OPS；不能由前端提供虚假的 OPS 归属字段。
- OPS 2FA 是另一套独立密钥。保管在服务器认证体系，只在创建时向授权 MASTER 展示绑定资料，**不得与邀请码混用**。登录时生成的六位动态验证码每 30 秒更换，**并不是**客户注册所需的邀请码。
- 生成的邀请码在总账户的已登记 OPS 列表中可复查，但旧格式邀请码必须标记“旧格式，禁止发放”；不能静默将旧格式当作新六位码。
- 现有 6 位邀请码具有有限熵，生产发布前需要审查恶意撞库风险、限速和验证码/CAPTCHA；不得在未完成安全验证时对外宣称安全完备。
- 本轮只更新隔离 GitHub 分支中的设计与源码，并未部署 Supabase Edge Function，也未修改数据库或任何已创建账户。

**独立验收用例**：
1. 创建 OPS-A，得到非空 TOTP 绑定密钥及恰好六位数字的邀请码（包括前导零）。
2. 创建 OPS-B，得到不同的 TOTP 绑定密钥和不同邀请码；数据库唯一索引强制不重复。
3. 用 OPS-A 邀请码注册客户，客户只归属 OPS-A；OPS-B 的列表查不到这个客户。
4. 错误的邀请码（非六位、含字母、停用、无效）一律无法注册。
5. 密钥重置只改变 OPS-A 的 2FA；不能意外改变 OPS-A 已发放的客户邀请码；暂停 OPS-A 后其邀请码拒绝新增注册。
6. 安全审计不能记录 TOTP 明文或客户注册密码；OPS 只能查询自己的客户。
